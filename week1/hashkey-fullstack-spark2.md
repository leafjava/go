## 二、Agent 框架 & 编排核心（必背，15 分钟深挖区）

**🗣️ 口述话术**：
> "框架上主要用 LangChain，自己也会做一些扩展。LangChain 我用得比较多的几个核心模块：模型抽象层（BaseLLM / ChatModel）、Chain 编排、Agent Executor、Memory 模块、Prompt Template、Output Parser 这几块。我自己在 LangChain 基础上扩展的主要是——Agent 的编排层，让多个 Agent 之间能像流水线一样协同工作，还有 Prompt 模板库（业务场景需要很多定制 prompt），输出侧的结构化校验（Pydantic 强制 JSON 输出），记忆管理这块也加了不少自己的策略，比如分层存储、上下文清洗。"

**回答框架**：

```
LangChain 核心模块使用：
- BaseLLM / ChatModel：模型抽象

- Memory：记忆

- OutputParser：结构化输出

自研扩展：
- 多 Agent 编排层（流水线协同）
```

### Q2: 编排做哪一块？为什么需要编排？你是怎么做的？（Q6 — STAR 必背）

**🗣️ 口述话术（STAR 框架）**：

> **S（场景）**：Agent BL 项目里要解决海运电子提单融资的风险评估，光靠一个 LLM 没法搞定——因为要同时考虑天气、航运、市场行情多个独立数据源，任何一个源挂了或者不准，结论都会偏。
>
> **T（任务）**：我负责设计 Agent 编排层，让多个专门 Agent 能协同工作，每个 Agent 负责一个数据源维度，最后汇总成一个决策。
>
> **A（行动）**：我设计了三条独立的 Agent——Weather Agent 拉气象数据、Risk Agent 拉航运 AIS 数据、Pricing Agent 拉市场行情——然后汇到一个 Decision Agent 做评分卡汇总。每条 Agent 独立超时、独立降级，缺数据就打缺省值而不是瞎猜。Agent 之间用结构化消息通信（JSON schema），输入输出格式、超时、配置都规范化。编排上有个关键原则：**流程状态机用代码写，LLM 只做推理节点**，不要让模型去编排流程，否则没法调试。
>
> **R（结果）**：风险评估从小时级压到分钟级，而且每次都有完整的数据溯源。这个编排方法论后来也用到了 Skill Space 项目上。

**STAR 记忆卡**：

```
S: 海运电子提单融资 = 多源风险评估，单 LLM 搞不定
T: 设计编排层，让 Weather/Risk/Pricing Agent 协同
A: 多 Agent 独立降级 + 结构化消息 + 流程用代码/推理用 LLM
R: 小时级 → 分钟级，有完整溯源
```

### Q3: 通用 Agent 编排能力（区别于固定工作流）— 这次面试官明确区分了！(Q7-Q8)

**🗣️ 口述话术**：
> "面试官您问的这个点很关键——我前面讲的 Agent BL 是**固定工作流编排**，每一步是写死的，适合业务明确、链路长的场景。但还有一类是**通用 Agent 编排**，你只给它一个目标，步骤不写死，让 LLM 自己决定下一步走哪，比如 Cursor / Claude Code / Cline 这种编程 Agent 就是典型例子。这块我在 Skill Space 项目里有做过——核心是给 LLM 暴露一个工具注册表（Tool Registry），写清楚每个 Skill 的功能描述、输入输出 schema，模型根据上下文动态决定下一步调哪个 Skill，不是按预设流程走。Skill 注册的时候我会暴露输入参数和格式，Agent 拿到之后先通过编排层理解当前上下文，再动态决定下一步走哪个工具，比如先搜索、再检查、再决定要不要扣分、再调用 Skill……逻辑链是模型推出来的，不是写死的。"

**回答框架**：

```
固定工作流编排 vs 通用 Agent 编排：

固定工作流（Agent BL）
  适用：业务明确、链路长、要可调试
  特征：流程用代码状态机，LLM 只做推理节点

通用 Agent 编排（Skill Space / Cursor / Cline）
  适用：目标开放、步骤灵活
  特征：工具注册表 + LLM 动态决策下一步
```

**关键点**：
- **这次面试官特别强调**：他问"通用 Agent 技能"和"编程 Agent 的目标达成"——他想听的是**后一种**
- **Skill Space 是讲通用编排能力的最佳素材**，要重点准备
- **不要混淆两种编排模式**：第一种是确定性优先，第二种是灵活性优先

### Q4: Skill Space 项目具体怎么做的？要不要调用工具跟 Skill 是谁决定的？(Q9-Q10)

**🗣️ 口述话术**：
> "Skill Space 的核心设计是三层——**Skill 注册层、编排层、执行层**。
>
> **Skill 注册层**：每个 Skill 注册的时候，我会暴露三件事——名称、功能描述、输入输出 schema。这是 Agent 能看到 Skill 的全部信息，描述写得好不好直接决定 Agent 会不会选对工具。
>
> **编排层**：这是最关键的一层——Agent 不是按预设流程走的，而是通过编排层理解当前上下文，动态决定下一步走哪个工具。比如用户要分析某高校并发送邀请，编排层会先让 Agent 搜索高校信息、检查匹配度、判断要不要扣分、再决定调用哪个 Skill 发通知。整个决策链是 LLM 推理出来的。
>
> **决策机制**：要不要调用工具、走哪条路，本质是 **LLM 推理 + 硬规则约束 + 置信度管理** 的组合。硬规则——比如某些操作必须满足前置条件才能执行；置信度管理——低置信度转人工复核或重试。"

**回答框架**：

```
Skill Space 三层架构：
① Skill 注册层：名称 + 描述 + 输入输出 Schema
② 编排层：理解上下文 → 动态决定下一步工具
③ 执行层：工具调用 + 结果回传

决策机制 = LLM 推理 + 硬规则约束 + 置信度管理
```

**关键点**：
- **"决策是 LLM 推理出来的"**——这句话这次面试官专门追问了
- **硬规则 + 软规则结合**：不能完全让 LLM 决定，要有兜底
- **置信度管理**：低置信度转人工 / 放弃 / 重试，三档处理

---

### Q5: 让 LLM 自主决定调用哪个工具，怎么做？(Q11 — 关键方法论)

**🗣️ 口述话术**：
> "让 LLM 自主做工具调用决策，核心是 **约束 + 描述 + 置信度** 三件事。
>
> **第一，工具注册表**——给 LLM 提供一份清晰的工具清单，每个工具写清楚功能描述、输入输出格式、适用场景。描述一定要写好，因为这是 LLM 选择的唯一依据。
>
> **第二，置信度阈值分级处理**——高置信度（>0.8）：直接采用结果；中等置信度（0.5-0.8）：重复检查 / 复核；低置信度（<0.5）：要么转人工，要么放弃推理结果。这是工具选择策略的核心。
>
> **第三，反馈闭环**——调用结果回传给 LLM，让它能根据结果决定下一步是重试、换工具还是结束。"

**回答框架**：

```
LLM 自主决策工具调用 = 工具注册表 + 置信度分级 + 反馈闭环

置信度分级处理：
高 (>0.8) → 直接采用
中 (0.5-0.8) → 复核
低 (<0.5) → 转人工 / 放弃
```

**关键点**：
- **置信度分级是这次面试官要的答案**——硬规则 + 置信度阈值
- **不要只说"让模型自己选"**，要给出具体策略

## 三、LangChain 源码级理解（必背，5 分钟）

### Q6: LangChain 怎么调大模型？那个接口看过吗？(Q12-Q13)

**🗣️ 口述话术**：
> "LangChain 调大模型的核心是通过**模型抽象层**——主要是 `BaseLanguageModel`（抽象基类）和 `BaseChatModel`（聊天模型基类），所有具体模型的实现（OpenAI、Anthropic、HuggingFace）都继承这两个基类。
>
> 调用方式主要是 `invoke` / `ainvoke`（异步）/ `stream`（流式）这三个方法。我常用的是 OpenAI 的实现，传 prompt 进去，它会帮我拼装请求体（messages 数组、temperature、max_tokens 这些参数），然后调用 OpenAI 的 API，返回响应后再解析成 LangChain 自己的 `AIMessage` 对象。
>
> 整个链路是：用户传 Prompt → LangChain 拼请求体 → 调模型 API → 解析响应 → 返回 `AIMessage`。这样做的最大好处是**模型无关性**——换模型只换一行代码，业务逻辑不用动。我读过这块的源码，对抽象层的设计印象很深——它用模板方法模式把通用流程放在基类，具体模型只实现自己的 `_call` 方法。"

**回答框架**：

```
LangChain 模型调用链路：

BaseLanguageModel（抽象基类）
  └── BaseChatModel（聊天模型基类）
        └── ChatOpenAI / ChatAnthropic / ...（具体实现）

调用方法：invoke / ainvoke / stream
链路：Prompt → 拼请求体 → 调 API → 解析响应 → AIMessage
设计模式：模板方法模式（基类定流程，子类实现 _call）
```

**关键点**：
- **提到 "BaseLLM 抽象层"**——面试官一听就知道你真看过源码
- **模板方法模式**——加分项，显得你有架构审美
- **模型无关性的好处**——业务逻辑不用动
- **如果追问 invoke 内部实现**：基类的 `invoke` 调用 `_generate` → `_agenerate`（异步）→ `_stream`（流式），子类只需要实现 `_call` 一个方法

## 四、记忆体系设计（必背，8 分钟）

### Q7: 你最熟悉的 Agent 部分是？(Q14 — 自我定位)

**🗣️ 口述话术**：
> "相对最熟悉的是**记忆方面**，特别是长期记忆和多轮上下文管理这块。短期记忆就是当前会话上下文，我一般用 `BufferMemory` 或者 `ConversationBufferWindowMemory`（带窗口的 buffer）做掉。但真正的难点是**长期记忆**——跨会话持久化，要分析用户历史行为和偏好，打上标签和时间戳存储。
>
> 还有个头疼的问题是**上下文污染**——比如工具调用返回了错误信息，如果不及时清理，模型会被带偏。所以记忆管理这块要有一套清洗策略：错误信息该清理就清理，过期的上下文该降级就降级。"

---

### Q8: 记忆怎么设计？短期 vs 长期怎么区分？(Q15-Q16)

**🗣️ 口述话术**：
> "记忆设计我分两层：**存储层 + 检索层**。
>
> **存储层**——分短期和长期两层。短期是会话级（当前对话上下文），用 buffer memory 实现，快进快出；长期是跨会话的，要持久化存储（向量数据库 + 关系数据库），存储的是用户历史行为、偏好、画像这种。每条长期记忆会打上**意图标签 + 时间戳**，方便后续匹配。
>
> **检索层**——短期直接从 buffer 取；长期要走相似度检索 + 标签过滤。
>
> **区分标准**——我设了一个**时间窗口机制**：比如 24 小时没被重新激活的记忆就降级处理（移到冷存储）；几分钟没交互的短期记忆直接清掉。判断标准主要是**时效性 + 频率**——用户最近反复提到的就保留，很久没提的就降级。"

**回答框架**：

```
记忆分层设计：

存储层：
  短期 = 当前会话上下文（BufferMemory）
  长期 = 跨会话持久化（向量库 + 关系库）
        ├── 用户历史行为
        ├── 偏好画像
        └── 标签 + 时间戳

检索层：
  短期：直接 buffer 取
  长期：相似度检索 + 标签过滤

区分标准：
  时效性 + 频率
  时间窗口：24 小时未激活 → 降级到冷存储
  短期：几分钟无交互 → 清掉
```

**关键点**：
- **时效性 + 频率** 是面试官要的答案
- **24 小时窗口降级** —— 这次面试官专门追问"短多久叫短"，要给出具体数字

## 七、快速记忆卡片

### LangChain 核心抽象（必背）
```
BaseLanguageModel（抽象基类）
  └── BaseChatModel（聊天模型）
        └── ChatOpenAI / ChatAnthropic / ...

调用方法：invoke / ainvoke / stream
设计模式：模板方法模式（基类定流程，子类实现 _call）
```

### 两种编排模式（必背）
```
固定工作流编排：业务明确、链路长，流程用代码状态机，LLM 只做推理节点
通用 Agent 编排：目标开放、步骤灵活，工具注册表 + LLM 动态决策
```

### LLM 自主决策工具调用（必背）
```
约束 + 描述 + 置信度

工具注册表：名称 + 描述 + 输入输出 Schema
置信度分级：
  高 (>0.8) → 直接采用
  中 (0.5-0.8) → 复核
  低 (<0.5) → 转人工 / 放弃
反馈闭环：结果回传模型，决定下一步
```

### Skill Space 三层架构（必背）
```
① Skill 注册层：名称 + 描述 + 输入输出 Schema
② 编排层：理解上下文 → 动态决定下一步工具
③ 执行层：工具调用 + 结果回传

决策机制 = LLM 推理 + 硬规则约束 + 置信度管理
```

### 记忆分层设计（必背）
```
存储层：
  短期 = 当前会话上下文（BufferMemory）
  长期 = 跨会话持久化（向量库 + 关系库）

检索层：
  短期：直接 buffer 取
  长期：相似度检索 + 标签过滤

区分标准：时效性 + 频率
时间窗口：24 小时未激活 → 降级到冷存储
短期：几分钟无交互 → 清掉
```

### Spark 深水区（面试官透露，必复述）
```
✅ 构建基本成功
⚠️ 现在的挑战：
  ① 业务理解（沟通 + 梳理需求）
  ② AI 对业务的理解（业务知识沉淀）
  ③ 准确性 + 稳定性
  ④ 安全（底线）
```
