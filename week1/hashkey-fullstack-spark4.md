## 二、核心问题 & 标准答案

### Q1: AI 检索合同（文档很大），上下文怎么管理？

**🗣️ 口述话术**：
> "大合同文档检索的上下文管理我分**四层**做：
>
> **① 文档预处理层**——合同进来先解析（PDF/Word），按章节拆分（甲方信息、标的、金额、条款、违约责任、争议解决），去掉页眉页脚、页码、广告这些噪声。
>
> **② 分块切片层**——按语义切片而不是固定长度。每个 chunk 保留：原文 + 章节标题 + 上下文摘要。chunk 之间留 10-15% 重叠，避免关键信息被切断。
>
> **③ 向量化 + 索引层**——用 Embedding 模型（bge-large-zh 这种）转成向量，存入向量库（pgvector / Milvus），同时建关键词倒排索引（BM25）做混合检索兜底。
>
> **④ 在线检索层**——用户问问题 → 向量化 → 混合检索（向量 + BM25）→ 重排（bge-reranker）→ top-k 段落拼成一个**简化的上下文窗口**（不超过模型 context 上限的 70%，留点空间给回答）→ 给 LLM。
>
> 关键工程点：**不要把整篇合同塞给 LLM**，必须先检索再压缩上下文，否则要么超限要么关键信息被淹没。"

**回答框架**：

```
大文档检索四层架构：

① 预处理：解析合同（PDF/Word）+ 章节拆分 + 去噪
② 分块：按语义切 + 保留章节标题 + chunk 重叠
③ 向量化：Embedding + 向量库 + BM25 倒排索引
④ 在线检索：query → 混合检索 → 重排 → 简化上下文 → LLM

红线：不要把整篇合同塞给 LLM
```

### Q2: 检索不准确 / 回答不准确怎么调优？

**🗣️ 口述话术**：
> "RAG 调优我按**问题分层定位 + 对症下药**做：
>
> **如果是检索层不准**（召不回相关内容）：
> - 加**重排模型**（bge-reranker、cohere-rerank），对召回的 top-100 精排到 top-5，提升精准度
> - 加**混合检索**（向量 + BM25），纯向量检索对专有名词、编号、缩写不敏感
> - 加**query 改写**（让 LLM 把用户口语化的问题改写成检索友好的形式）
> - 调**分块策略**（按语义切而不是固定长度，加 chunk 重叠）
>
> **如果是生成层不准**（检索到了但回答错）：
> - 检查**Prompt 模板**——是否强制要求'只能引用检索内容，不要自由发挥'
> - 加**结构化输出**（让模型输出 JSON 字段：答案 + 引用编号 + 置信度）
> - 加**引���溯源**——强制模型标注每个论断来自哪个 chunk，没引用的不输出
>
> **兜底机制**：
> - **低置信度拒答**——置信度 < 阈值直接说"知识库没这个内容"，转人工
> - **反馈闭环**——把答错的 case 收集起来，定期优化分块/Prompt
>
> 工程经验：**重排 + 混合检索**是性价比最高的两个优化，能解决 80% 的检索不准问题。"

**回答框架**：

```
RAG 调优对症下药：

检索层不准（召不回）：
  → 重排模型（bge-reranker）
  → 混合检索（向量 + BM25）
  → query 改写
  → 调分块策略

生成层不准（答错）：
  → Prompt 约束（只引用检索内容）
  → 结构化输出（JSON + 引用编号）
  → 强制引用溯源

兜底：
  → 低置信度拒答 + 转人工
  → 反馈闭环 + 持续优化

性价比之选：重排 + 混合检索
```

### Q3: 0-1 项目从设计稿到交付，怎么和 AI 配合？有哪些好用的 Skill？

**🗣️ 口述话术**：
> "0-1 项目我和 AI 配合走**五步法**：
>
> **① 需求解析**——把产品文档 / 设计稿丢给 Claude Code，让它生成需求清单（功能点 + 边界 + 验收标准），我审一遍补充遗漏。
>
> **② 项目结构搭建**——直接让 Claude Code 生成脚手架（前端 React + Vite，后端 Go/Gin + 项目目录结构 + 配置文件 + README），5 分钟出基础框架。
>
> **③ 节点拆分 + 任务交付**——把需求拆成 5-10 个可独立交付的节点（建库 → 后端 API → 前端页面 → 对接 → 测试），每个节点对应一个 PR，让 AI 逐个生成代码。
>
> **④ 端到端测试**——用 AI 生成测试用例（单测 + 集成测试），重点是**端到端流程**（从用户点击到后端响应），不是覆盖率。
>
> **⑤ 交付质量保证**——AI 生成代码不直接合并，自己 review 一遍（diff 喂给 LLM 做 code review，找 bug 和风格问题），确认 OK 再提交。
>
> **好用的 Skill 推荐**（基于 Claude Code / Cursor）：
> - **代码生成**：直接说'生成 XX 功能的 React 组件，用 Tailwind + TypeScript'
> - **Bug 定位**：贴报错日志让 AI 分析
> - **重构**：让 AI 按 SOLID 原则重构现有代码
> - **测试生成**：让 AI 给函数生成单测
> - **文档**：让 AI 写 README / API 文档 / 注释
>
> 关键经验：**AI 是助手不是替代品**——它生成代码，我负责审、测试、上线，全程把控质量。"

**回答框架**：

```
0-1 项目 AI 配合五步法：

① 需求解析：产品文档 → AI 生成需求清单 → 补充遗漏
② 脚手架：AI 生成项目结构（5 分钟搞定）
④ 节点拆分：拆 5-10 个独立交付节点，逐个 PR
⑤ 端到端测试：AI 生成测试用例 + 流程验证
⑥ 交付质量：AI 生成 + 人工 review diff

好用的 Skill：
  代码生成 / Bug 定位 / 重构 / 测试生成 / 文档

红线：AI 生成不等于 AI 负责，全程把控
```

### Q4: AI 工作流自己搭过吗？（LangGraph）

**🗣️ 口述话术**：
> "搭过，我用 **LangGraph** 搭过多 Agent 工作流——比如 Agent BL 项目里，多个 Agent 协同做海运风险评估。
>
> LangGraph 我用得比较多的几个核心模块：
>
> **① 图结构定义**——用 `StateGraph` 定义流程，每个节点是一个 Agent（天气 Agent、风险 Agent、定价 Agent），节点之间用边连接，边可以加条件判断（'置信度高→自动执行'，'置信度低→人审'）。
>
> **② 节点注册**——每个节点是一个函数，参数是 state，输出是更新后的 state。函数里实现 Agent 的逻辑（调 LLM / 调 API / 写库）。
>
> **③ 状态管理**——用一个 `State` TypedDict 定义全局状态（用户输入、中间结果、最终输出），每个节点读 state 写 state，状态���转一目了然。
>
> **④ 工具绑定**——Agent 节点里用 `bind_tools` 把工具（查询天气、查询船舶 AIS）注册进去，Agent 自己决定调哪个。
>
> **⑤ 回溯调试**——图结构本身就能可视化（LangGraph Studio），出问题能回溯到任意节点，看当时的状态和决策。
>
> 我用 LangGraph 而不是 LangChain 主要是两个原因：一是图结构清晰，业务方能看懂流程；二是天然支持人审节点（`interrupt`），合规场景必须。"

**回答框架**：

```
LangGraph 五大核心模块：

① 图结构：StateGraph（节点 + 边 + 条件判断）
② 节点注册：每个节点 = 一个函数（读 state，写 state）
③ 状态管理：State TypedDict（全局状态流转）
④ 工具绑定：bind_tools（Agent 自己选工具）
⑤ 回溯调试：LangGraph Studio 可视化

选 LangGraph 原因：
  - 图结构清晰（业务方能看懂）
  - 天然支持人审节点（合规刚需）
```

### Q5: 多 Agent 协作数据怎么流转？每个节点输出是什么？

**🗣️ 口述话术**：
> "多 Agent 数据流转我用一个 **State 对象**做中心化流转，类似 redux 的思路。
>
> **State 结构**（TypedDict）：
> ```python
> class WorkflowState(TypedDict):
>     user_input: str                    # 用户原始输入
>     weather_result: Optional[Dict]    # Weather Agent 输出
>     risk_result: Optional[Dict]       # Risk Agent 输出
>     pricing_result: Optional[Dict]    # Pricing Agent 输出
>     final_decision: Optional[Dict]    # Decision Agent 输出
>     confidence: float                  # 综合置信度
>     audit_log: List[Dict]              # 全链路审计日志
> ```
>
> **每个 Agent 节点的输出格式**（统一规范）：
> ```python
> {
>   "agent_name": "weather_agent",
>   "conclusion": "检测到台风'山竹'，预计影响航程 2-3 天",
>   "confidence": 0.85,
>   "data_source": ["meteorology_api", "historical_typhoon_db"],
>   "raw_data": {...},   # 原始数据，方便回溯
>   "timestamp": "2026-01-15T10:30:00Z"
> }
> ```
>
> **流转逻辑**——三个子 Agent（weather/risk/pricing）并行执行，各自更新 state 的对应字段；汇总到 Decision Agent 时，Decision Agent 读三个字段 + 综合计算 → 输出最终决策 + 置信度。
>
> **置信度路由**：
> - 高置信度（>0.8）→ 自动执行
> - 中置信度（0.5-0.8）→ 自动 + 人工复核（异步）
> - 低置信度（<0.5）→ 转人审节点
>
> **关键设计**：每个 Agent 输出必须有 `conclusion + confidence + data_source` 三件套，下游才能决策。"

**回答框架**：

```
多 Agent 数据流转 = State 中心化 + 统一输出格式

State 结构：
  user_input + 各 Agent 结果 + final_decision + confidence + audit_log

每个 Agent 输出三件套：
  conclusion（结论）+ confidence（置信度）+ data_source（数据源）

流转逻辑：
  3 个子 Agent 并行 → Decision Agent 汇总 → 置信度路由

置信度路由：
  高 (>0.8) → 自动
  中 (0.5-0.8) → 自动 + 异步复核
  低 (<0.5) → 转人审
```

### Q6: Telegram 病毒增长循环 Skill 的输入、执行过程、K 因子怎么算？

**🗣️ 口述话术**：
> "Telegram 病毒增长循环这个 Skill 是我在 Skill Space 项目里做的，核心思路是**让分享变得智能**。
>
> **Skill 输入**：
> - 当前用户 ID
> - 当前内容（链接 / 文章 / 商品）
> - 用户行为上下文（最近分享过什么 / 兴趣标签 / 好友关系链）
>
> **执行过程**（三步）：
>
> **① 判断分享时机**——不是每次都弹分享按钮，而是看：
> - 用户刚消费完有价值内容（读完文章 / 完成任务）
> - 用户行为触发条件（解锁成就 / 获得优惠）
> - 避免打扰（短时间内不重复触发）
>
> **② 生成分享内容**——不是机械转发，而是 AI 帮生成个性化文案：
>   - 根据好友兴趣生成不同版本
>   - 根据内容类型（文章/商品）调整文案风格
>   - 附带预览卡片（提升点击率）
>
> **③ 自然分发**——通过 Telegram 的消息分享机制，让分享看起来像朋友推荐而不是广告。
>
> **K 因子计算**（病毒系数）：
> ```
> K = 每个用户平均邀请人数 × 邀请转化率
>
> 例子：
> 每个用户平均邀请 5 个好友
> 邀请链接的点击转化率 30%
> 注册转化率 60%
> K = 5 × 0.30 × 0.60 = 0.9
>
> K > 1：病毒传播（用户指数增长）
> K = 1：稳态传播（线性增长）
> K < 1：传播停滞（衰减）
> ```
>
> **为什么 AI 比规则系统强**——规则系统只能机械触发（每分享 1 次奖励 10 积分），AI 能：
> - 精准判断最佳分享时机
> - 生成个性化文案（提升点击率）
> - 识别高质量分享者（重度用户）做差异化激励
>
> 我的实现里 K 因子从原来规则的 0.3 提升到了 1.4。"

**回答框架**：

```
Telegram 病毒增长 Skill：

输入：
  用户 ID + 内容 + 行为上下文

执行三步：
  ① 判断时机（消费完成 / 触发条件 / 避免打扰）
  ② AI 生成个性化文案（不同好友不同版本）
  ③ 自然分发（看起来像朋友推荐）

K 因子公式：
  K = 邀请人数 × 邀请转化率 × 注册转化率
  K > 1 → 病毒传播
  K = 1 → 稳态
  K < 1 → 衰减

AI vs 规则系统：
  精准时机 + 个性化文案 + 差异化激励
  K 因子从 0.3 → 1.4
```

### Q7: MCP vs Function Calling / 注册表的区别

**🗣️ 口述话术**：
> "这两者我都用过，主要差异是**标准化程度 + 复用性**：
>
> **Function Calling（注册表模式）**——
> - 模型厂商自己定义的工具调用协议（OpenAI function calling、Anthropic tool use）
> - 工具描述写在每次请求的 `tools` 参数里
> - 跨模型不兼容（OpenAI 的格式 Claude 用不了，要转换）
> - **优点**：简单直接，集成快
> - **缺点**：每换一个模型都要适配一遍
>
> **MCP（Model Context Protocol）**——
> - Anthropic 2024 年推出的**开放协议**，类似 LLM 领域的 USB-C
> - 工具/资源/提示词标准化，模型无关
> - 一次开发，多模型复用（OpenAI、Claude、本地模型都能用）
> - 客户端-服务器架构：MCP Client 调 LLM，MCP Server 暴露工具

### Q8: Go 高并发原理，goroutine vs 线程

**🗣️ 口述话术**：
> "Go 高并发核心是 **goroutine + GMP 调度模型**。
>
> **线程 vs Goroutine 对比**：
>
> | 维度 | 线程（OS Thread） | Goroutine |
> |------|------------------|-----------|
> | 创建开销 | 1-2 MB 栈空间 | 初始 2 KB，按需扩到 GB |
> | 调度 | 内核调度（系统调用） | 用户态调度（Go runtime） |
> | 上下文切换 | 需要切换到内核态（成本高） | 用户态切换（成本低） |
> | 可创建数量 | 千级（受内存限制） | 百万级 |
> | 通信方式 | 共享内存 + 锁 | Channel（推荐）/ 共享内存 |
>
> **GMP 模型**：
> - **G（Goroutine）**：协程本身
> - **M（Machine）**：操作系统线程，真正执行 G
> - **P（Processor）**：逻辑处理器，调度 G 到 M 上执行，默认 = CPU 核数
>
> **调度流程**：每个 P 维护一个本地 G 队列，P 周期性地从全局队列偷 G（work stealing），保证负载均衡。G 在阻塞时（M 阻塞），runtime 会把 M 上的其他 G 转移到新 M 上继续执行。
>
> **AI 时代 Go 的优势**：
> 1. **部署效率高**——单个二进制文件，无依赖，容器友好（Docker 镜像几十 MB，Python 几百 MB）
> 2. **并发性能好**——AI 服务是 I/O 密集（等 LLM 响应），goroutine 天然合适
> 3. **生态成熟**——AI 网关、向量库客户端、监控 SDK 都有
> 4. **相对 Java**——启动快、资源占用低（Java JVM 启动 1-2 秒，Go 几十 ms），K8s 扩缩容友好
> 5. **相对 Python**——性能强 50-100 倍，做网关/聚合层/限流/审计比 Python 稳
> 6. **相对 PHP**——原生支持高并发（PHP-FPM 进程模型，并发受限于进程数）
>
> 所以 Go 在 AI 时代的定位很清晰：**网关 + 高并发基础设施**，Python 做 AI 编排，两者混合架构最常见。"

**回答框架**：

```
goroutine vs 线程：

线程：1-2MB 栈 + 内核调度 + 千级并发 + 共享内存
goroutine：2KB 栈 + 用户态调度 + 百万级并发 + Channel

GMP 模型：
  G = 协程，M = 线程，P = 处理器（=CPU 核数）
  P 本地队列 + 全局队列 + work stealing 负载均衡

AI 时代 Go 优势：
  ① 部署快（单二进制，无依赖）
  ② 并发好（I/O 密集天然合适）
  ③ 启动快（K8s 扩缩容友好）
  ④ 性能强（比 Python 快 50-100 倍）
  ⑤ 资源占用低（比 Java JVM 轻量）

定位：网关 + 高并发基础设施
Python 做 AI 编排 → 混合架构
```

### Q9: MySQL 表结构设计规范

**🗣️ 口述话术**：
> "MySQL 表结构设计我遵循**七大规范**：
>
> **① 命名规范**——表名、字段名用 `小写字母 + 下划线`（蛇形命名），不用驼峰、不用拼音。

>

> - 高频查询字段（where、order by、join）

>
> **⑤ 范式化**——业务表做到**第三范式**（3NF），减少数据冗余；宽表/读多写少场景可以适当反范式（用冗余换 JOIN 性能）。
>
> **⑥ 必备字段**——每张表加 `id`、`created_at`、`updated_at`、`is_deleted`（软删除）、`created_by`、`updated_by`，方便审计和追踪。
>
> **⑦ 注释完整**——表注释 + 字段注释（特别是枚举值），后续维护者一眼能看懂。
>
> 实战经验：**索引设计是性能的关键**——好的索引能让查询从秒级降到毫秒级，差的索引（或没有索引）能把数据库打死。"
